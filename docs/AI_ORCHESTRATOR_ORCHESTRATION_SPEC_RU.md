# AI Orchestrator: спецификация оркестрации

- Статус: предлагаемая техническая спецификация
- Область: расширение и webview AI Code Orchestrator / AI Orchestrator
- Язык: русский перевод; пользовательский текст может быть локализован
- Целевая совместимость: существующие режимы, профили провайдеров, история задач, делегирование, контрольные точки и поведение с одной активной задачей

## 1. Контекст и соответствие репозиторию

Репозиторий уже предоставляет примитивы, необходимые оркестратору:

- Режимы представлены встроенными или пользовательскими записями `ModeConfig` с определениями ролей, инструментами, ограничениями и инструкциями. `.agent-modes` проверяется по `schemas/agent-modes.json`.
- Профили провайдеров сохраняются через `ProviderSettingsManager`; `currentApiConfigName` выбирает активный профиль, а `modeApiConfigs` уже сопоставляет slug режимов с ID профилей.
- Задачи сохраняются как элементы истории и поддерживают отношения родитель/потомок, вложенное делегирование, переходы статусов, сохранение истории API/UI, контрольные точки, возобновление, отмену и события задач.
- `Task.startSubtask()` и `ClineProvider.delegateParentAndOpenChild()` реализуют делегирование на основе метаданных. Завершение родительской задачи сейчас возобновляет ее через `reopenParentFromDelegation()` и добавляет результат дочерней задачи в историю UI и API.
- Webview содержит разделы настроек, поиск и выбор режимов, средства выбора провайдера/модели, историю задач с рекурсивными строками подзадач и паттерны сообщений/событий хоста расширения.

Оркестратор должен расширять эти примитивы, а не создавать вторую систему задач. Существующее поведение без оркестрации остается неизменным.

## 2. Цели

1. Изменить поведение существующего режима `orchestrator`, чтобы он действовал как тимлид реальной команды: был связующим звеном между пользователем-заказчиком и агентами-исполнителями, понимал цель и общее состояние разработки, декомпозировал работу, распределял ее и отвечал за итоговое качество, не погружаясь без необходимости во все детали реализации.
2. Расширить существующий профиль провайдера назначениями моделей по ролям. Профиль, как и сейчас, содержит настройку провайдера и основной модели, но дополнительно хранит выбранную модель для каждой роли. Ненастроенная роль использует основную модель этого же профиля. Выбор отдельного профиля для каждой роли не требуется.
3. Позволить оркестратору анализировать и планировать, а затем по своему решению распараллеливать независимые части работы между любыми доступными текущими режимами. Например, одну задачу можно разделить между двумя исполнителями режима `code` и двумя исполнителями режима `debug`, если это безопасно и возможно; необходимость такого разделения определяет оркестратор как тимлид. Каждый исполнитель получает только свой узкий, достаточный для качественной работы контекст и не хранит всю задачу целиком.
4. Сохранять качество посредством явных контрактов, валидации, рецензирования, доработки и контролируемой интеграции.
5. Снижать стоимость и задержку, централизуя дорогостоящий архитектурный контекст и предоставляя исполнителям узкий контекст конкретной задачи.
6. Сделать оркестрацию наблюдаемой, управляемой, отменяемой, восстанавливаемой и безопасной для рабочей области.
7. Сохранить обратную совместимость текущего выбора режима, конфигурации провайдера, делегирования, истории, контрольных точек и API.

## 3. Нецели первого выпуска

- Распределенное выполнение между машинами или пользователями.
- Автоматические коммиты/отправка в удаленные репозитории без явного указания пользователя в задаче. Если пользователь явно запросил коммит или отправку, это выполняется по действующим правилам одобрения команд и внешних побочных эффектов.
- Неограниченные автономные циклы или неограниченный обмен сообщениями между моделями.
- Замена существующего движка выполнения чатов/задач.
- Гарантия бесконфликтного параллельного редактирования без явного этапа интеграции.
- Хранение секретов провайдера в записях оркестрации.

## 4. Область продукта и UX

### 4.1 Точки входа

- Использовать существующий встроенный slug режима `orchestrator` и изменить его поведение на оркестрацию.
- Если выбран режим `orchestrator` (он выбран по умолчанию), создается обычная корневая задача, выполнение которой идет по протоколу оркестрации.
- Если пользователь вручную выбирает отдельную роль/режим, этот режим работает как сейчас и не запускает оркестрацию.
- Заголовок чата показывает `Orchestrator`, текущую фазу, число активных дочерних задач, расход бюджета и управление отменой/паузой.
- Существующий `new_task` остается допустимым. В режиме `orchestrator` он используется для запланированного запуска дочерней задачи по протоколу оркестратора; в обычном режиме выбранной роли сохраняет текущее поведение.

### 4.2 UX настроек

Добавить раздел настроек `Orchestration`, видимый во время внедрения за флагом эксперимента/функции:

- Включение оркестрации.
- В настройках каждого существующего профиля провайдера — таблица назначений моделей для `orchestrator` и любых доступных slug режимов, включая `architect`, `code`, `debug` и `reviewer`.
- Каждая строка назначения поддерживает `Использовать основную модель` (по умолчанию) либо выбор другой модели, доступной через провайдера данного профиля, а также сводку возможностей модели.
- Отдельная фиксированная роль `worker` не обязательна: исполнителями являются существующие режимы, а оркестратор может запускать несколько экземпляров одного режима параллельно.
- Максимум параллельных исполнителей, максимальная глубина оркестрации, бюджет стоимости/токенов на запуск и дочернюю задачу, тайм-аут, лимит повторов/доработок.
- Политика контекста: минимальная, сбалансированная (по умолчанию) или полная; список разрешенных файлов/каталогов; право исполнителей редактировать; необходимость одобрения интеграции.
- Политика рецензирования: отключено, по завершении, после каждого пакета или только для рискованных изменений.
- Политика конфликтов: изолированное рабочее дерево, артефакт патча/индекса, сериализованная общая рабочая область или остановка при конфликте.
- Управление одобрением человеком для записи, команд, вызовов MCP, интеграции и окончательного завершения.
- Сброс к значениям по умолчанию, проверка конфигурации и отображение предупреждений о неразрешенных профилях/моделях.

Использовать устоявшиеся паттерны настроек: навигацию и поиск разделов в `SettingsView`, элементы `Select`/поиска моделей, `setCachedStateField`, метаданные профилей провайдера и сообщения webview. Не показывать ключи API в этом UI или артефактах задач.

### 4.3 UX времени выполнения

Панель оркестрации должна показывать:

- Сводку плана и граф зависимостей.
- Карточки дочерних задач с ролью, названием задачи, моделью/профилем, статусом, прошедшим временем, расходом токенов/стоимости, измененными файлами, тестами и последним отчетом.
- Действия: отменить дочернюю задачу, повторить, доработать, рецензировать, открыть задачу, просмотреть diff, одобрить интеграцию, приостановить/возобновить запуск.
- Четкое различие между `planned`, `running`, `awaiting review`, `needs rework`, `ready to integrate`, `integrated`, `failed`, `canceled` и `blocked`.
- По умолчанию компактные отчеты; полные расшифровки доступны при открытии дочерней задачи.
- Никакого фиктивного прогресса: статус управляется событиями и сохраняется.

## 5. Терминология и роли

- **Запуск**: одно выполнение корневой оркестрации.
- **Оркестратор/тимлид**: управляющий агент и связующее звено между пользователем-заказчиком и исполнителями. Владеет целью, планом, зависимостями, распределением задач, бюджетом, шлюзами качества и итоговым результатом, но хранит преимущественно обобщенное состояние и не забивает контекст деталями каждой реализации.
- **Планировщик/архитектор**: может быть самим оркестратором или отдельной ролью; создает исполняемый план.
- **Исполнитель**: агент реализации или исследования, который знает свой ограниченный участок работы и получает только необходимый для него контекст, критерии и зависимости.
- **Рецензент**: соответствует штатному slug `reviewer`; проверяет критерии приемки, тесты, безопасность и регрессии; не изменяет код незаметно. Подробное определение роли — в разделе 24.
- **Доработчик**: исполнитель, получающий структурированные замечания рецензии и ограниченную задачу исправления.
- **Интегратор**: применяет одобренные патчи/объединяет изолированную работу и запускает интеграционную проверку.
- **Основная модель профиля**: выбранная в существующем профиле модель по умолчанию. Все назначения ролей внутри этого профиля используют ее, если для роли явно не выбрана другая модель.

Имена ролей — стабильные идентификаторы; slug режимов остаются источником разрешений инструментов и конфигурации промпта. Пользовательский режим можно назначить роли без изменения его определения.

## 6. Маршрутизация моделей

### 6.1 Приоритет разрешения

Для каждого вызова сначала определить активный профиль существующим механизмом, а затем разрешить закрепленный `ModelRoute` внутри этого профиля:

1. Явное назначение модели в запросе дочерней задачи, если оно разрешено политикой.
2. Модель, назначенная роли в активном профиле.
3. Основная модель активного профиля.

Провайдер, API, учетные данные и прочие параметры берутся из активного профиля. Назначение роли меняет модель внутри профиля, а не переключает роль на другой профиль. Существующий `modeApiConfigs` может определять активный профиль режима до разрешения модели, но не заменяет назначения моделей по ролям внутри профиля. Эти правила разрешения одинаково распространяются на все штатные роли, включая `reviewer`.

Разрешенный маршрут закрепляется за попыткой задачи. Последующие изменения настроек не изменяют активную попытку.

### 6.2 Форма маршрута

```ts
interface ModelRoute {
	profileId: string
	provider: string
	modelId: string
	role: string
	source: "explicit" | "role" | "primary"
	contextWindow?: number
	maxOutputTokens?: number
	reasoningEffort?: string
	resolvedAt: number
}
```

Перед запуском проверять доступность провайдера/модели, списки разрешений организации, возможности, размер контекстного окна, поддержку инструментов и учетные данные. Если назначенная модели нет в активном профиле или она недоступна, показать ошибку и предложить выбрать другую модель либо вернуть назначение к основной модели профиля. Нельзя незаметно переключаться на другой профиль, провайдера или неожиданно дорогую модель.

### 6.3 Политика стоимости

Отслеживать входные, кэшированные входные, выходные токены, токены рассуждений, оценочную стоимость и маршрут модели для каждой попытки. Резервировать бюджет до запуска, сверять фактическое использование после завершения и освобождать неиспользованный резерв. Оркестратор может понижать класс модели только по явной резервной политике. Исчерпание бюджета блокирует новую работу, но разрешает синтез завершенных результатов.

## 7. Модель данных

Сохранять метаданные оркестрации отдельно от секретов провайдера, предпочтительно в совместимом с историей/метаданными задач хранилище с версионированием схемы.

```ts
type OrchestrationRunStatus =
	| "planning"
	| "planned"
	| "dispatching"
	| "running"
	| "reviewing"
	| "reworking"
	| "integrating"
	| "synthesizing"
	| "completed"
	| "failed"
	| "canceled"
	| "paused"

type ChildStatus =
	| "planned"
	| "blocked"
	| "running"
	| "awaiting_review"
	| "needs_rework"
	| "ready_to_integrate"
	| "integrated"
	| "failed"
	| "canceled"

interface OrchestrationRun {
	schemaVersion: 1
	runId: string
	rootTaskId: string
	status: OrchestrationRunStatus
	goal: string
	planVersion: number
	nodeIds: string[]
	settingsSnapshot: OrchestrationSettings
	createdAt: number
	updatedAt: number
	budget: BudgetLedger
	activeNodeIds: string[]
	eventSequence: number
	cancellationRequested?: boolean
	error?: ErrorRecord
}

interface OrchestrationNode {
	nodeId: string
	runId: string
	taskId?: string
	role: string
	mode: string
	title: string
	objective: string
	dependsOn: string[]
	status: ChildStatus
	attempt: number
	maxAttempts: number
	inputContract: ContextContract
	outputContract?: ResultContract
	route?: ModelRoute
	artifactRefs: string[]
	reviewRefs: string[]
	conflictRefs: string[]
	timestamps: Record<string, number>
	error?: ErrorRecord
}
```

История задач остается долговечной пользовательской записью. `parentTaskId`, ID дочерних задач, существующие метаданные делегирования, контрольные точки и события задач должны заполняться, чтобы история и возобновление работали для обычных и оркестрируемых задач.

## 8. Жизненный цикл и конечный автомат оркестрации

### 8.1 Жизненный цикл

1. **Прием**: создать корневую задачу, зафиксировать снимок настроек, закрепить основной маршрут, проверить разрешения и бюджет.
2. **Анализ**: оркестратор изучает цель пользователя и релевантный контекст рабочей области.
3. **Планирование**: создать структурированный DAG узлов, зависимостей, владения, критериев приемки, областей файлов, рисков и оценок бюджета.
4. **Шлюз плана**: проверить схему, циклы, дублирование владения, неподдерживаемые режимы и бюджет. Запросить одобрение пользователя, если настроено.
5. **Запуск**: создать дочерние задачи через существующую фабрику делегирования/задач с метаданными родителя/запуска/узла. Запустить все готовые по зависимостям узлы в пределах лимита параллелизма.
6. **Выполнение**: дочерние задачи работают с узким контекстом и изолированными ресурсами. Собирать сигналы активности и долговечные события.
7. **Пакетный шлюз**: после завершения пакета оркестратор получает компактные отчеты, обновляет готовность зависимостей и решает: продолжить/рецензировать/доработать/блокировать.
8. **Рецензирование**: запустить настроенного рецензента для артефактов, тестов и контракта узла.
9. **Доработка**: преобразовать замечания в ограниченные узлы исправления; ограничить попытки и сохранить происхождение.
10. **Интеграция**: применить одобренные артефакты в порядке зависимостей, явно разрешить конфликты, выполнить интеграционные проверки.
11. **Синтез**: оркестратор проверяет глобальную цель, суммирует изменения, тесты, риски и нерешенные вопросы.
12. **Завершение**: сохранить итоговый результат, метрики и ссылки на дочерние задачи; возобновить обычный поток завершения задачи.

### 8.2 Правила переходов состояний

- `planning -> planned` только при допустимом DAG и резервировании бюджета.
- `planned -> dispatching -> running`, когда запущен хотя бы один узел.
- `running -> reviewing`, когда выполнен настроенный шлюз рецензирования.
- `running -> blocked`, когда зависимость завершилась ошибкой или обязательный ресурс недоступен.
- `awaiting_review -> needs_rework|ready_to_integrate` на основе структурированных замечаний.
- `needs_rework -> running` только с новой попыткой и оставшимся бюджетом.
- `ready_to_integrate -> integrated` только после проверки конфликтов и требуемого одобрения.
- Любое нетерминальное состояние может перейти в `paused` или `canceled`; отмена сначала кооперативная, после тайм-аута — принудительная.
- Терминальные состояния неизменяемы, кроме административных записей исправления.

Переходы должны быть идемпотентными, нумероваться последовательностью, сохраняться до публикации события и отклонять устаревшие команды.

## 9. Контракты контекста

По умолчанию оркестратор не должен передавать полную расшифровку корневой задачи. Каждая дочерняя задача получает подписанный/версионированный `ContextContract`:

```ts
interface ContextContract {
	contractVersion: 1
	runId: string
	nodeId: string
	goal: string
	objective: string
	acceptanceCriteria: string[]
	constraints: string[]
	mode: string
	fileScopes: { include: string[]; exclude: string[] }
	dependencySummaries: Array<{ nodeId: string; summary: string; artifactRefs: string[] }>
	relevantFacts: string[]
	allowedTools: string[]
	allowedCommands?: string[]
	outputRequirements: string[]
	tokenBudget: number
	parentContextDigest: string
}
```

Исполнители должны возвращать `ResultContract`, содержащий статус, краткую сводку, прочитанные/измененные файлы, ссылки на артефакты, тесты и точные результаты, допущения, риски, нерешенные вопросы и предлагаемые следующие действия. Расшифровки не заменяют контракт. Сжатие контекста может суммировать старые материалы, но должно сохранять критерии, ограничения, область файлов, решения и дайджесты.

По умолчанию включение контекста сбалансировано: цель и критерии, релевантные файлы, правила области, сводки зависимостей и только текущие diff. Секреты, несвязанная история задач и полные расшифровки других задач исключаются. Оркестратор получает сводки и выбранные артефакты, а не все токены исполнителей. Для предотвращения переполнения контекста использовать существующий механизм сжатия контекста, если он уже реализован в продукте, с порогами и сохранением обязательных критериев, ограничений, областей файлов, решений и дайджестов. Не создавать отдельную систему сжатия без необходимости.

## 10. Параллельное выполнение и конфликты

- Построить DAG; узлы без неудовлетворенных зависимостей могут работать параллельно до `maxParallelWorkers`.
- Владение файлами объявляется в плане. Два узла с правом записи не могут совместно использовать файл, если план явно этого не разрешает.
- Предпочитать изолированные рабочие деревья или артефакты патчей. Если они недоступны, использовать блокировку рабочей области и сериализовать пересекающиеся области.
- Перед интеграцией сравнивать базовую ревизию, затронутые пути, хеши и сгенерированные артефакты. Обнаруживать текстовые и семантические конфликты.
- Безопасное автообъединение ограничено непересекающимися файлами или детерминированными непересекающимися фрагментами. Все прочие конфликты становятся записями `conflict` и требуют интегратора/доработки либо одобрения пользователя.
- Никогда незаметно не отбрасывать артефакт дочерней задачи. Сохранять отклоненные патчи и объяснять причину.
- Узлы исследования только для чтения могут работать широко, но должны соблюдать правила игнорирования и политику конфиденциальности.

## 11. Рецензирование, доработка и интеграция

Рецензент получает контракт узла, diff артефакта, базовое состояние, критерии приемки, диагностику и результаты тестов. Замечания имеют серьезность (`blocker`, `major`, `minor`, `note`), ссылки на файл/строку, доказательства и рекомендации по исправлению.

- Замечания `blocker`/`major` направляются на доработку; `minor` могут быть приняты только согласно политике.
- Доработка создает новую попытку, связанную с исходным узлом и ID замечаний; история не перезаписывается.
- Максимальное число циклов рецензирования/доработки ограничивается бюджетами запуска и узла.
- Интеграция — отдельный шлюз. Интегратор применяет артефакты в детерминированном порядке, запускает сначала целевые, затем интеграционные тесты и формирует отчет.
- При сбое интеграции создать узел конфликта/доработки с доказательствами сбоя; не отмечать запуск завершенным.
- Итоговый синтез должен включать принятые и отклоненные изменения, тесты, стоимость, маршруты моделей, риски и последующую работу.

## 12. Схема настроек

Добавить версионированную схему в общие типы, используя принятые в репозитории соглашения Zod:

```ts
interface ProfileRoleModelSettings {
	// Хранится внутри существующего профиля провайдера.
	roleModels: Record<
		string,
		{
			modelId?: string
			inheritPrimary?: boolean
		}
	>
}

interface OrchestrationSettings {
	enabled: boolean
	orchestratorModeSlug: string // "orchestrator"
	maxParallelWorkers: number // 1..32, default 4
	maxDepth: number // 1..8, default 3
	maxRunTokens?: number
	maxRunCost?: number
	maxChildTokens?: number
	maxChildCost?: number
	timeoutMs: number
	maxReworkAttempts: number
	contextPolicy: "minimal" | "balanced" | "full"
	conflictPolicy: "isolated" | "patch" | "serialized" | "stop"
	reviewPolicy: "off" | "completion" | "batch" | "risk"
	requirePlanApproval: boolean
	requireIntegrationApproval: boolean
	allowWorkerCommands: boolean
	allowWorkerMcp: boolean
	persistTranscripts: boolean
}
```

`ProfileRoleModelSettings` является частью каждого существующего профиля провайдера, а не отдельной таблицей маршрутов на профили. Проверять, что назначенная модель доступна у провайдера данного профиля. `inheritPrimary` используется по умолчанию для каждой роли, включая `orchestrator`, `architect`, `code`, `debug` и `reviewer`. Хранить только ID моделей; провайдер, API и учетные данные уже принадлежат профилю. Использовать версию миграции и сохранять неизвестные будущие поля там, где это допускают существующие соглашения импорта/экспорта.

## 13. API и интерфейсы

Ввести внутреннюю границу сервиса, чтобы оркестрацию можно было тестировать без связывания конечного автомата с UI:

```ts
interface OrchestratorService {
	start(input: StartOrchestrationInput): Promise<OrchestrationRun>
	dispatch(runId: string): Promise<void>
	handleChildEvent(event: ChildEvent): Promise<void>
	approvePlan(runId: string): Promise<void>
	approveIntegration(runId: string): Promise<void>
	retryNode(runId: string, nodeId: string): Promise<void>
	cancel(runId: string, reason?: string): Promise<void>
	pause(runId: string): Promise<void>
	resume(runId: string): Promise<void>
	getSnapshot(runId: string): Promise<OrchestrationSnapshot>
}
```

Обязательные сообщения/события: `orchestrationStarted`, `planReady`, `nodeStatusChanged`, `nodeReport`, `reviewFinding`, `conflictDetected`, `budgetUpdated`, `orchestrationPaused`, `orchestrationCompleted` и `orchestrationError`. События содержат `runId`, применимый `nodeId`, монотонную последовательность, временную метку, статус и отредактированную полезную нагрузку.

Существующие события `TaskDelegated`, `TaskSpawned`, `TaskDelegationCompleted` и события возобновления продолжают отправляться для совместимости. Добавлять специфичные для оркестрации события, не меняя смысла кортежей.

## 14. Сохранение, восстановление и отмена

- Атомарно сохранять снимки запуска и узлов с упреждающей записью события или эквивалентной транзакционной последовательностью.
- При активации сканировать нетерминальные запуски, проверять схему, восстанавливать индексы в памяти и согласовывать истории дочерних задач.
- Запущенный узел без терминального результата дочерней задачи получает `running`/`recovering`; возобновить его, если задача допускает это, иначе отметить ошибкой с восстанавливаемой ошибкой.
- Сохранять ключи идемпотентности для команд запуска, рецензирования, интеграции и переходов, предотвращая дублирование дочерних задач или объединений.
- Контрольные точки фиксируют базу интеграции и состояние артефактов. Восстановление может вернуть последнюю одобренную точку интеграции без удаления истории аудита.
- Отмена долговечно фиксирует намерение, прекращает новые запуски, отправляет отмену активным задачам, ожидает ограниченный льготный период и затем записывает принудительную отмену. Уже интегрированная одобренная работа автоматически не откатывается.
- Пауза прекращает новые запуски и позволяет активным исполнителям завершиться или отменяет их согласно политике.

## 15. Бюджеты токенов и эффективность

Использовать иерархические бюджеты: запуск, фаза, узел, попытка и запрос. Резервировать оценочные токены до вызовов; соблюдать жесткие пределы; показывать мягкие предупреждения на 70/85/100 процентах. Предпочитать:

- более сильную модель этого же профиля для планирования, сквозных решений, арбитража рецензий и итогового синтеза;
- более экономичные специализированные модели этого же профиля для ограниченных задач `code`/`debug`/`worker`, если они назначены;
- компактные контракты результатов и ссылки на артефакты вместо передачи расшифровок;
- кэшированные стабильные инструкции и правила репозитория, если позволяют возможности провайдера;
- пакетирование независимых запусков и сводок событий;
- раннюю остановку избыточных узлов и детерминированных сбоев инструментов.

Метрики должны сравнивать оценочную и фактическую стоимость, а также экономию токенов с базовым вариантом без оркестрации. Запуск должен оставаться корректным при отсутствии данных о стоимости; показывать `unknown`, а не выдумывать значения.

### 15.1 Оптимизация контекста и повторного использования

Оптимизация контекста дополняет иерархию бюджетов из раздела 15 и направлена на сокращение объема повторно вычисляемых и повторно передаваемых данных без потери корректности. Оркестратор применяет перечисленные ниже механизмы совместно, адаптируя стратегию под возможности активной модели.

#### 15.1.1 Динамический приоритизированный контекст

Контекст формируется динамически под каждую задачу, а не собирается один раз для всего запуска. Элементы контекста получают приоритет в зависимости от текущей задачи, ее критериев приемки и области файлов. В модель отправляется не весь проект, а только релевантная его часть; низкоприоритетные элементы исключаются или выносятся в сводки.

#### 15.1.2 Локальный кэш по content digest

Вычисляемые представления проекта кэшируются локально: AST, символы, зависимости, результаты поиска, embeddings, summaries и прочие производные представления. Каждая запись кэша привязана к hash / content digest исходных данных, чтобы неизменившиеся входные данные не пересчитывались повторно. При изменении content digest соответствующая запись инвалидируется и пересчитывается.

#### 15.1.3 Дедупликация

Одинаковый контент не отправляется модели повторно. Дублирование устраняется между системным контекстом, контекстом задачи и результатами инструментов: повторяющиеся фрагменты заменяются ссылками на уже переданное представление. Дедупликация не должна удалять данные, требуемые контрактом задачи.

#### 15.1.4 Стабильный префикс для prompt caching провайдера

Там, где провайдер поддерживает prompt caching, стабильная часть prompt / context prefix (системная политика, правила репозитория, инвариантные инструкции) сохраняется неизменной между запросами. Изменяющаяся часть контекста размещается строго после стабильного prefix, чтобы кэш провайдера оставался валидным и переиспользовался.

#### 15.1.5 Возможности адаптера провайдера

Адаптер провайдера сообщает оркестратору, какие возможности поддерживает модель: prompt caching, context caching, structured output, tool calling и прочие. Оркестратор адаптирует стратегию оптимизации под возможности конкретной модели: например, применяет стабильный prefix только при поддержке prompt caching и использует structured output там, где он доступен.

#### 15.1.6 Бюджет токенов и резерв под ответ

Для каждой задачи существует token budget в рамках иерархии бюджетов раздела 15. Часть бюджета заранее резервируется под ответ модели, поэтому входные данные не могут израсходовать весь контекст. Резерв под вывод сохраняется даже при агрессивной оптимизации входного контекста.

#### 15.1.7 ContextContract и ResultContract

Каждый node/task имеет контракт требуемого контекста, а результат задачи — структурированный контракт результата. Следующая задача получает не весь предыдущий диалог, а только необходимый результат предыдущей. Определения интерфейсов `ContextContract` и `ResultContract` приведены в разделе 9 и здесь не переопределяются; оптимизация контекста опирается на них как на границу передачи данных между узлами.

#### 15.1.8 Предотвращение повторной отправки файлов

Уже переданные модели неизменившиеся файлы повторно не отправляются. Повторная передача происходит только при изменении content hash файла либо при необходимости другого представления того же файла (например, иной диапазон строк или иной уровень детализации). Состояние переданных файлов отслеживается по content digest в рамках попытки задачи.

#### 15.1.9 Метрики

Система измеряет эффективность оптимизации: input tokens, output tokens, cached tokens, размер контекста, cache hit/miss, объем повторно переданных данных, стоимость и эффективность context selection. Эти метрики публикуются в структурированную телеметрию согласно разделу 16 и не должны содержать секретов или полного содержимого промптов.

#### 15.1.10 Корректность важнее оптимизации

Оптимизация не должна приводить к потере необходимой информации. При конфликте между экономией токенов и корректностью решения приоритет всегда у корректности: обязательные критерии, ограничения, области файлов, решения и дайджесты из раздела 9 сохраняются даже ценой большего расхода токенов.

## 16. Наблюдаемость

Локально и, необязательно, через существующие средства журналирования записывать структурированную очищенную телеметрию:

- ID запуска/узла, ID родительской задачи, роль, режим, источник маршрута, ID провайдера/модели (без ключей), переходы состояний, ожидание в очереди, длительность, повторы;
- входные/выходные/кэшированные токены и токены рассуждений, оценочную стоимость, бюджетные решения;
- файлы и хеши артефактов, тесты/коды выхода, замечания рецензии, конфликты, причину отмены;
- ID корреляции и последовательность событий для каждой видимой пользователю операции.

Предоставить отладочный экспорт с секретами и содержимым промптов, отредактированными по умолчанию. Полные промпты/расшифровки журналировать только при явном включении. Панели и диагностические команды можно добавить позже; первый выпуск требует доступной для поиска диагностики в канале вывода и сведений о запуске в UI.

## 17. Безопасность и защита

- Применять существующие ограничения рабочей области, `.aicoignore`, группы инструментов режима, правила защищенных файлов, одобрение команд, разрешения MCP и списки разрешенных моделей организации к каждой дочерней задаче.
- Дочерняя задача не может повысить права инструментов или расширить область файлов изменением отчета либо запросом другой роли.
- Проверять все созданные моделью планы и аргументы инструментов по схемам и текущим разрешениям.
- Считать вывод и артефакты исполнителя недоверенным вводом оркестратора; отделять и проверять их.
- Не помещать ключи API, секреты, дампы окружения или несвязанные приватные файлы в контракты контекста, журналы, экспорт или отчеты.
- Требовать одобрения человеком рискованных команд, внешних побочных эффектов, интеграции и окончательного завершения согласно настройкам.
- Не допускать, чтобы инъекция промпта из содержимого репозитория переопределяла политику оркестрации; системная политика и контракты остаются главными.

## 18. Совместимость и миграция

- Существующие режимы и обычные задачи выполняются точно как прежде, когда оркестрация отключена или режим не `orchestrator`.
- Существующий `modeApiConfigs` продолжает выбирать профиль для режима по прежним правилам.
- Существующие профили провайдеров остаются единицей хранения и расширяются необязательным сопоставлением `роль -> модель`. При отсутствии сопоставления используется основная модель профиля.
- Существующая история родительских/дочерних задач и вложенное делегирование остаются читаемыми. Оркестрируемые узлы добавляют метаданные, не требуя их понимания старыми клиентами.
- Отсутствующие настройки оркестрации мигрируют к значениям по умолчанию: отключено, все роли наследуют основную модель, сбалансированный контекст, один или четыре исполнителя согласно решению по внедрению продукта (рекомендуется четыре при включении), без автоматического обхода одобрения интеграции.
- Неизвестные роли переходят к основной модели с предупреждением. Удаленные профили используют резерв только при явной настройке; иначе блокируются с UI исправления.
- Экспорт/импорт включает настройки оркестрации с версией схемы, исключает секреты и сообщает о пропущенных недопустимых маршрутах.

## 19. Стратегия тестирования

### Модульные тесты

- Настройки Zod, разрешение маршрутов, приоритеты, проверка возможностей, арифметика бюджета, редактирование секретов, проверка DAG, обнаружение циклов, владения/конфликтов и защиты переходов состояний.
- Построение и усечение контракта контекста сохраняет обязательные поля.
- Идемпотентная обработка событий, предотвращение повторного запуска, отклонение устаревшей последовательности, лимиты повторов, отмена и согласование восстановления.

### Интеграционные тесты

- Оркестратор создает дочерние задачи через `delegateParentAndOpenChild` и сохраняет метаданные родителя.
- Независимые узлы запускаются параллельно; зависимые ожидают.
- Завершение дочерней задачи создает компактные контракты результатов и совместимые с прежней системой события завершения/возобновления делегирования.
- Замечания рецензента создают ограниченные попытки доработки; одобренные артефакты интегрируются; конфликты блокируют интеграцию.
- Разрешение модели работает для явного назначения, назначения роли и основной модели внутри выбранного профиля; назначение роли не меняет профиль или провайдера.
- Сохранение/импорт/миграция настроек и сообщения webview работают при отсутствующих или недопустимых назначениях моделей.
- Перезапуск расширения восстанавливает нетерминальные запуски без дублирования дочерних задач или объединений.

### UI- и сквозные тесты

- Селектор режимов и таблица маршрутизации настроек, наследование/сброс, ошибки валидации, оптимистичное состояние и несохраненные изменения.
- Граф запуска, обновления статусов дочерних задач, раскрытие отчета, ссылки на diff/тесты, повтор/доработка/отмена/пауза/возобновление, одобрения плана/интеграции.
- Доступность: навигация с клавиатуры, подписи, объявления статусов и узкие макеты webview.
- Отображение стоимости/токенов и редактирование секретов.

### Тесты производительности и сбоев

- DAG из 32 узлов с ограниченным параллелизмом, контекст большого репозитория, медленные/сбойные провайдеры, ограничения частоты, некорректные планы модели, отказ инструмента, конфликты рабочей области, перезапуск на каждой фазе и гонки отмены.

## 20. План внедрения

1. Реализовать общие схемы, разрешение маршрутов и встроенный режим за флагом функции без автоматической параллельной записи.
2. Добавить сервис оркестратора и долговечный жизненный цикл, используя артефакты патчей и по умолчанию одного исполнителя.
3. Добавить шлюзы рецензента/доработки и интегратора; включить настраиваемый параллелизм и изолированные рабочие деревья.
4. Открыть настройки и UI времени выполнения; провести внутреннее использование с телеметрией и аварийным выключателем.
5. Постепенно увеличивать параллелизм по умолчанию только после достижения порогов приемки качества, восстановления и стоимости.
6. На протяжении внедрения сохранять глобальный выключатель и безопасный переход к обычному выполнению `code`/`architect`.

## 21. Критерии приемки

- Пользователь может выбрать `orchestrator`, отправить цель, увидеть проверенный план и одобрить или отклонить его.
- Каждый вызов роли отображает и сохраняет активный профиль и разрешенную внутри него модель; ненастроенные роли наследуют основную модель этого профиля.
- Не менее двух независимых дочерних задач выполняются параллельно, если позволяет параллелизм, а зависимости выполняются по порядку.
- Исполнители получают только объявленные контракт контекста и области; оркестратор получает краткие отчеты и артефакты.
- Замечания рецензии надежно приводят к доработке или приемке; интеграция обнаруживает и показывает конфликты без потери данных.
- Существующая история задач, вложенное делегирование, контрольные точки, возобновление, отмена, разрешения режимов, списки разрешений провайдеров и обычные режимы остаются работоспособными.
- Перезапуск в любой нетерминальной фазе восстанавливает работу или явно отмечает ее без повторного запуска или объединения.
- Бюджеты запуска и дочерних задач предотвращают перерасход, показывают фактическое использование, когда оно доступно, и останавливают новую работу при жестких пределах.
- UI поддерживает статусы, отчеты, diff, тесты, повтор/доработку, отмену, паузу/возобновление и одобрения с доступными элементами управления.
- Тесты безопасности демонстрируют отсутствие утечки секретов и повышения привилегий через вывод модели.
- Автоматические тесты охватывают жизненный цикл, маршрутизацию, контекст, параллелизм, конфликты, рецензирование/доработку, сохранение, миграцию и потоки UI.

## 22. Решения по реализации

- Использовать существующую подсистему рабочих деревьев и другие доступные механизмы продукта везде, где это возможно. Для каждого узла с правом записи предпочтительно применять изоляцию; при пересечении областей обязательно проверять конфликты и явно интегрировать результат.
- В первом выпуске `orchestrator` является тимлидом и главным координатором. `architect` и другие доступные режимы выступают исполнителями, которых оркестратор назначает по содержанию задачи; отдельный обязательный узел `architect` не вводится.
- Использовать существующие механизмы локальной телеметрии и журналирования, если они уже есть. Отдельную систему телеметрии в первом выпуске не создавать; при отсутствии существующих механизмов полагаться на обязательные диагностические события и сведения о запуске в UI.
- Рецензент использует модель, назначенную его роли в активном профиле, либо основную модель этого профиля; назначение роли не переключает провайдера или API.
- Итоговая интеграция должна быть отдельным контролируемым этапом: ее может выполнять оркестратор как тимлид, если нет конфликтов и политика это разрешает; при конфликтах или необходимости сложного объединения работу передавать специализированному интегратору. Это позволяет назначить более сильную модель управляющим ролям, а более экономичные — исполнителям, не смешивая профили.

Эти решения зафиксировать в версии схемы и покрыть тестами миграции и приемки.

## 23. Поддержка Float Encoding для OpenAI-Compatible Embeddings

Цель: добавить в Codebase Indexing опцию выбора формата эмбеддингов base64 / float для OpenAI-compatible провайдеров. Это позволяет корректно работать с провайдерами, возвращающими обычный числовой массив `float[]`, не изменяя существующее поведение для провайдеров, отдающих base64.

### 23.1 Настройка

- Добавить параметр `codebaseIndexOpenAiCompatibleUseFloatEncoding: boolean`.
- В UI Codebase Indexing добавить чекбокс `Use Float Encoding`.
- Значение `false` — текущее поведение (base64); значение `true` — отправлять `encoding_format: "float"`.

### 23.2 OpenAICompatibleEmbedder

- Передать настройку `useFloatEncoding` в `OpenAICompatibleEmbedder`.
- При запросе к `/embeddings` использовать `encoding_format: useFloatEncoding ? "float" : "base64"`.
- Поддержать оба варианта ответа: `embedding: number[]` и `embedding: string` (base64).
- Для float использовать числовой массив непосредственно, без base64-декодирования.

### 23.3 Validation

- `validateConfiguration()` должен использовать тот же `encoding_format`, что и обычные embedding-запросы.
- Проверять: HTTP-запрос успешно выполнен; поле `data` присутствует; `embedding` имеет ожидаемую размерность; для текущей модели Nemotron — 2048.

### 23.4 Model Dimension

- Не изменять существующую систему определения размерности.
- Если модель отсутствует в `embeddingModels.ts`, использовать вручную заданный `modelDimension = 2048`.

### 23.5 Обратная совместимость

- По умолчанию `useFloatEncoding = false`.
- Все существующие OpenAI-compatible конфигурации продолжают работать через base64.
- Изменение настройки не должно затрагивать OpenAI и другие embedding providers.

### 23.6 Тесты

Добавить тесты на:

- base64 → корректное декодирование;
- float → `number[]` возвращается без преобразования;
- validation с float;
- validation с base64;
- проверку размерности embedding;
- сохранение/загрузку новой настройки.

### 23.7 Результат

OpenAI-compatible провайдеры, возвращающие обычный `float[]` (например NVIDIA Nemotron через AnyModel), должны полноценно работать с Codebase Indexing без изменения существующего поведения для base64-провайдеров.

## 24. Штатная роль reviewer

### 24.1 Назначение и статус роли

Роль `reviewer` выполняет ревью кода: проверяет соответствие критериям приемки, тесты, безопасность и регрессии. Рецензент не изменяет код незаметно, а выдает структурированные замечания. Правки по замечаниям выполняет роль доработчика (см. раздел 11).

Роль является штатной (встроенной), с собственным slug `reviewer`, по аналогии с `architect`, `code`, `debug` и `orchestrator`. Оркестратор может вызывать `reviewer` при необходимости в соответствии с `reviewPolicy` из раздела 12 и жизненным циклом раздела 8 (шаг рецензирования в разделе 8.1 и правила переходов в разделе 8.2).

Роли `reviewer` можно назначить отдельную модель через `ProfileRoleModelSettings.roleModels`, как и остальным ролям; по умолчанию действует `inheritPrimary` — используется основная модель активного профиля. Разрешение модели для роли `reviewer` подчиняется общим правилам маршрутизации раздела 6.

### 24.2 Ограничения инструментов

Рецензент работает преимущественно в режиме чтения и анализа: чтение файлов, поиск, запуск тестов и диагностики. Рецензент не выполняет незаметных правок кода. Все изменения кода идут через роль доработчика по структурированным замечаниям рецензии. Ограничения инструментов, области файлов и разрешения применяются к задаче рецензента согласно разделу 17.

### 24.3 Структура замечания

Формат структурированных замечаний рецензии (серьезность, ссылки на файл/строку, доказательства, рекомендации) определен в разделе 11. Структура одного замечания приведена ниже как TypeScript-интерфейс:

```ts
interface ReviewFinding {
	findingId: string
	runId: string
	nodeId: string
	severity: "blocker" | "major" | "minor" | "note"
	title: string
	filePath?: string
	line?: number
	evidence: string
	recommendation: string
	acceptanceCriterionRef?: string
}
```

Замечания `blocker`/`major` направляются на доработку; `minor`/`note` могут быть приняты только согласно политике (раздел 11).

### 24.4 Промпты роли

### 24.5 Интеграция
